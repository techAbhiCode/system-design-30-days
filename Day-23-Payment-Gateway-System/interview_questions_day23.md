# 6 Essential Interview Questions: Day 23 (Payment Gateway LLD)

### 1. Why did you use the Template Method Pattern instead of the Strategy Pattern for the payment execution flow (`validate` -> `initiate` -> `confirm`)?
**Answer:** The **Strategy Pattern** is designed to swap entire algorithms interchangeably (like swapping `PaytmBankingSystem` for `RazorpayBankingSystem`). However, the payment execution lifecycle has an invariant, non-negotiable skeleton: we *must* always validate first, then initiate/debit, and finally confirm. If we used only Strategy here, individual gateway implementations could reorder, skip, or omit critical steps like validation or confirmation. The **Template Method Pattern** strictly guarantees the sequence in the abstract base class while letting subclasses customize the specific implementation of each step.

### 2. How does the Proxy Pattern handle retries, and why choose Proxy over the Decorator Pattern or hardcoded loops?
**Answer:** The **Proxy Pattern** acts as a surrogate for the real gateway, implementing the exact same interface (`PaymentGateway`). When `processPayment()` is called, the proxy intercepts the call and runs a loop with maximum retry attempts if transient failures occur. 
* **Why not hardcode it inside the gateway?** Hardcoding retry logic inside `PaytmGateway` violates the **Single Responsibility Principle (SRP)**. The gateway's job is to talk to Paytm, not manage network retry policies.
* **Why Proxy over Decorator?** A Decorator is intended to augment or add new behaviors/responsibilities to an object (e.g., adding logging, compression, or timestamps). A Proxy is intended to control access, manage lifecycle, or add transparent resilience (caching, security, retries) without altering the interface or client expectations.

### 3. How do you prevent duplicate charges if a network timeout occurs right after the bank debits the user's account?
**Answer:** We enforce **Idempotency** using an `Idempotency-Key` (a unique UUID generated by the client per payment attempt):
1. When the payment request arrives at the Gateway, it checks a distributed cache (e.g., Redis) using `SETNX` (atomic insert with TTL) on `idempotency:<key>`.
2. If the key already exists and has a status of `PROCESSING` or `SUCCESS`, the gateway immediately rejects duplicate processing or returns the cached transaction response.
3. When sending the debit request to the downstream bank/processor, the gateway passes this same idempotency key in the banking API header. Even if the network drops on the return trip and the gateway retries, the downstream bank recognizes the key and will not double-debit the customer.

### 4. Real-world bank transactions are asynchronous (e.g., 3D-Secure OTP or UPI approval). How does this design transition from synchronous to asynchronous processing?
**Answer:** In the current LLD, `processPayment()` returns a synchronous boolean for simulation. In production:
1. `initiatePayment()` transitions the payment status in the database to `PENDING` and returns a redirection URL or deep-link token to the user for OTP/UPI verification.
2. The user completes the 2FA authentication on the banking app/page.
3. The bank asynchronously sends an HTTP POST callback (**Webhook**) with the signed transaction status to our Webhook Handler endpoint.
4. The Webhook Handler verifies the cryptographic signature (HMAC-SHA256), transitions the payment status to `SUCCESS` or `FAILED`, and notifies the merchant.
5. In case webhooks are delayed or dropped, a background **Reconciliation Cron Worker** periodically polls the bank's status API for any transactions stuck in `PENDING` after a timeout (e.g., 10 minutes).

### 5. How would you handle intelligent dynamic routing between multiple payment providers?
**Answer:** Instead of the client or a static factory deciding whether to use Paytm or Razorpay, we introduce a **Smart Routing Engine** inside the gateway:
* The Routing Engine monitors real-time health metrics (success rates, latency) and commercial agreements (transaction fee percentages).
* If Bank A's success rate drops below 70%, the routing engine trips a **Circuit Breaker** and automatically redirects subsequent transactions to Bank B.
* For large merchants, transactions can also be split via weighted load-balancing (e.g., 70% to Razorpay, 30% to Paytm) to optimize volume discounts and redundancy.

### 6. Why are `GatewayFactory`, `PaymentService`, and `PaymentController` Singletons, and how do you ensure thread safety in a multi-threaded web server?
**Answer:** They are Singletons because they represent stateless, centralized coordination components across the application. Creating new instances for every HTTP request would create unnecessary garbage collection overhead and make centralized state management impossible.
* In a multi-threaded production environment (e.g., Spring Boot handling thousands of concurrent requests), the `PaymentService` must be thread-safe. 
* In our prototype, `setGateway()` modifies a shared field, which would cause race conditions if multiple threads set different gateways simultaneously.
* **The Production Fix:** In production, we make the service completely stateless by passing the target gateway or request context directly into the method call (`processPayment(gateway, request)`), or we resolve the gateway per-request from an application context/DI container without mutating shared singleton instance variables.
